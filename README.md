# Домашнее задание по SDN — Flow Monitoring & Anomaly Detection

**Спецкурс «Современные облачные технологии» · 2026 · 10 баллов**

В этой работе необходимо разработать SDN-приложение на **OSKen / OpenFlow 1.3**, способное наблюдать за потоками виртуальных машин и автоматически реагировать на аномально высокую интенсивность трафика.

## Что должно получиться

```text
                    +--------------------+
                    | OSKen Controller   |
                    |                    |
                    | FlowStatsRequest   |
                    | pps / bps          |
                    | Anomaly Detection  |
                    +----------+---------+
                               | OpenFlow 1.3
                    +----------v---------+
                    |   Open vSwitch s1  |
                    +-----+-----+-----+--+
                          |     |     | \
                         h1    h2    h3 h4
                      10.0.0.1 ...   10.0.0.4
```

Первое задание — **измерение трафика** с помощью OpenFlow-счётчиков. Второе — **временная блокировка IPv4-трафика источника**, превысившего заданный порог.

**Важно:** обнаружение «аномалии» в этом задании означает превышение явно заданного порога pps, а не машинное обучение, поиск DDoS-атак или полноценную IDS.

## Подготовка окружения

Рекомендуется **Ubuntu 22.04 / Python 3.10 или 3.11** или аналогичная Linux-машина с Python 3.10 или 3.11, OVS и Mininet. Для сетевой эмуляции нужны Linux namespaces и права root; запуск на Windows/macOS без Linux VM не предусмотрен.

```bash
sudo apt-get update
sudo apt-get install -y openvswitch-switch mininet iputils-ping python3-venv
sudo systemctl enable --now openvswitch-switch
python3 -m venv --system-site-packages .venv
source .venv/bin/activate
python3 -m pip install -r requirements.txt
```

`--system-site-packages` нужен, чтобы Python из venv видел системный модуль Mininet. Не требуется устанавливать пакет Mininet через pip. Если вы используете другой дистрибутив Linux, установите Mininet и OVS из его пакетного менеджера.

**Выполняйте команды из корневой директории репозитория.**

## Задание 1 — Мониторинг сетевых потоков (6 баллов)

Разработайте приложение, которое с периодичностью, указанной в `config/monitor.json`, запрашивает у каждого подключённого коммутатора статистику **IPv4 forwarding flow entries** посредством `OFPFlowStatsRequest` и обрабатывает ответы `EventOFPFlowStatsReply`.

В готовом L2-коммутаторе правила обычной IPv4-пересылки имеют:

- `priority=100`;
- cookie `FORWARD_COOKIE` (константа из `common/forwarding.py`);
- матчинг по `in_port`, `eth_type=0x0800`, `ipv4_src`, `eth_dst`;
- счётчики `packet_count` и `byte_count`.

Не учитывайте table-miss, ARP, блокирующие правила и другие записи OpenFlow. Для преобразования полученных объектов OSKen в независимые от OpenFlow структуры используйте предоставленную функцию `common.ofp_helpers.forwarding_counters`.

### Часть 1. Периодический опрос (2 балла)

В файле `tasks/task_1/task.py` реализуйте:

1. Отправку запросов `OFPFlowStatsRequest` на подключённые datapath.
2. Связь запроса с ответом по `xid` (не путайте ответы от разных опросов).
3. Сбор составных ответов OpenFlow, если установлен флаг `OFPMPF_REPLY_MORE`.
4. Обработку зависшего запроса, чтобы при потере ответа последующие опросы продолжались.
5. Передачу завершённого среза счётчиков в `publish_sample(dpid, monotonic_timestamp, counters)`.

Используйте `time.monotonic()`, а не системные часы для вычисления интервалов измерения. Готовый цикл `hub.sleep` уже предоставлен.

### Часть 2. Вычисление интенсивности (3 балла)

В `tasks/task_1/monitor.py` реализуйте `FlowRateTracker.update(...)`.

Исходные значения `packet_count` / `byte_count` — **накопительные счётчики конкретной flow-записи**, а не скорость. Для каждого IPv4-источника `src_ip` необходимо вычислить:

```text
pps = сумма положительных Δpacket_count / Δtime
bps = сумма положительных Δbyte_count * 8 / Δtime
```

Условия:

- В одной записи статистики могут встречаться несколько flow от одного IP; их скорости суммируются.
- Первый срез каждого коммутатора используется как базовый: `pps=0`, `bps=0`.
- Для вновь появившегося flow предыдущего значения нет: его счётчик **не должен** ошибочно считаться приростом.
- Если flow удалён, его старый счётчик не должен создавать отрицательную скорость.
- Если счётчик сбросился, отрицательное изменение считается нулевым приростом; следующее измерение производится от нового базового значения.
- Нулевой или отрицательный интервал времени не должен приводить к делению на ноль или к отрицательной скорости.
- Состояние разных datapath (`dpid`) хранится раздельно; при переподключении коммутатора вызывается `reset(dpid)`.

### Часть 3. Результат и наблюдаемость (1 балл)

Используйте готовую функцию `publish_sample`: она экспортирует результаты в JSON, сортирует наиболее активные источники и пишет измерения в лог.

Пример результата в `runtime/metrics.json`:

```json
{
  "generated_at": "2026-10-29T15:00:00+00:00",
  "switches": {
    "1": {
      "monotonic_timestamp": 12345.0,
      "sources": {
        "10.0.0.1": {"packets": 840, "bytes": 70560, "pps": 80.0, "bps": 53760.0}
      },
      "top_talkers": [{"src_ip": "10.0.0.1", "pps": 80.0}],
      "blocked": []
    }
  }
}
```

`packets` и `bytes` здесь — суммы текущих накопительных счётчиков активных flow; **не путайте их со скоростью**. Значения приводятся только в качестве примера.

## Задание 2 — Обнаружение аномалий и блокировка (4 балла)

На основе приложения задания 1 реализуйте политику безопасности: если фактическая скорость источника **строго больше** заданного порога `max_pps`, его IPv4-трафик временно блокируется средствами OpenFlow.

Конфигурация `config/policies.json`:

```json
{
  "rules": [
    {"src_ip": "10.0.0.1", "max_pps": 40, "block_seconds": 10},
    {"src_ip": "10.0.0.2", "max_pps": 100, "block_seconds": 8}
  ]
}
```

Для источников, не перечисленных в `rules`, автоматическая блокировка **не выполняется**. Лимиты и длительность блокировок задаются отдельно для каждого IP.

### Часть 1. Логика детектора (2 балла)

Реализуйте `PolicyEngine` в `tasks/task_2/policy.py`:

- Проверка конфигурации (корректный IPv4, `max_pps >= 0`, `block_seconds` — положительное целое число, отсутствие повторяющихся IP).
- `evaluate(dpid, timestamp, rates)` — выдаёт **только новые** `BlockDecision` для источников, превысивших порог.
- Повторная блокировка уже заблокированного источника не производится до истечения срока.
- `active(dpid, timestamp)` возвращает текущие блокировки для экспорта в JSON.
- `reset(dpid)` удаляет состояние одного коммутатора.

### Часть 2. OpenFlow-блокировка (2 балла)

В `tasks/task_2/task.py` реализуйте реакцию на решения детектора:

- Создайте `OFPFlowMod` с `priority=300` (выше обычного forwarding).
- Матчинг: `eth_type=0x0800, ipv4_src=<заблокированный IP>`.
- Пустые действия/инструкции (`drop`).
- Установите `hard_timeout=block_seconds`: коммутатор **сам** удалит запрет при истечении срока, без перезапуска и без ручного удаления.
- Нельзя блокировать ARP, IPv4 других источников или весь порт целиком.
- По возможности отражайте блокировки в логах и в поле `blocked` JSON-метрик.

**Обратите внимание:** длительность блокировки в контроллере отсчитывается с момента принятия решения и может немного расходиться с временем принятия FlowMod коммутатором. В тестах допускается небольшая погрешность времени реального удаления OpenFlow-правила.

## Запуск и проверка

### Шаг 1. Проверка Python-логики

Тесты не требуют root, OVS и OSKen:

```bash
python3 -m pytest -q
```

**До выполнения задания тесты должны падать** — это ожидаемое поведение шаблона. Для успешного выполнения необходима реализация заданий.

### Шаг 2. Запуск контроллера

**Терминал 1 — контроллер (задача 1):**

```bash
source .venv/bin/activate
osken-manager --ofp-tcp-listen-port 6653 tasks/task_1/task.py
```

Для задания 2 вместо этого запускайте только:

```bash
osken-manager --ofp-tcp-listen-port 6653 tasks/task_2/task.py
```

Не запускайте оба контроллера одновременно на одном TCP-порту.

**Терминал 2 — Mininet:**

```bash
sudo "$(which python3)" tasks/task_1/mininet_cli.py
# Для задания 2: sudo "$(which python3)" tasks/task_2/mininet_cli.py
```

Пример команд в CLI Mininet:

```text
mininet> pingall
mininet> h1 ping -c 5 10.0.0.4
mininet> h1 ping -i 0.01 -c 300 10.0.0.4
mininet> sh ovs-ofctl -O OpenFlow13 dump-flows s1
```

Для задания 1 ожидается положительная скорость `pps` у активного источника в `runtime/metrics.json`. Для задания 2 после превышения порога должен появиться `priority=300` с `actions=drop`, который автоматически исчезнет после `hard_timeout`. На включение блокировки требуется хотя бы два корректных среза счётчиков.

**Терминал 3 — просмотр метрик:**

```bash
watch -n 1 cat runtime/metrics.json
```

Очистка Mininet после прерванного запуска:

```bash
sudo mn -c
```

### Шаг 3. Cетевой smoke-test

Сначала запустите соответствующий контроллер из шага 2, а затем в отдельном терминале:

```bash
sudo "$(which python3)" tests/integration/check_live.py --task 1
# или --task 2
```

Проверяет доступность VM, появление ненулевой метрики и (для задачи 2) факт установки drop-правила. Требует работающий OVS, Mininet, IPv4 ping и Linux root. **Этот тест не заменяет модульные тесты и не является исчерпывающим.**
